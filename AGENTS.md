# AGENTS.md

Instructions for any AI agent (or human) working in this repo.

## Style rules (hard rules)

- **No em dashes, anywhere**: code, comments, commit messages, PRs, docs,
  chat output. Use a comma, colon, parentheses, or a separate sentence
  instead. Regular hyphens in compound words are fine.
- No AI co-author trailers or "Generated with" footers in commits, PRs,
  or docs. The human user is the sole author of record.

Before committing, grep the diff for em dashes and fix any hits:

```bash
git diff --cached | grep -n "—"
```

## Tagging and releasing

Releases are cut by pushing a semver tag. That triggers
`.github/workflows/release.yml`, which builds the MSI with WiX v5 and
attaches it to a GitHub Release.

1. Make sure `main` is green (check the CI workflow badge/run).
2. Pick the next version. This project does not yet track a version file;
   the tag itself is the source of truth and flows into the MSI's
   `ProductVersion` via `-Version` in `installer/build-installer.ps1`.
3. Tag and push:

   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

4. Watch the "Release" workflow run in GitHub Actions. On success it:
   - publishes a self-contained `win-x64` build,
   - packages it into `modshell-hwtest-X.Y.Z.msi` via WiX v5,
   - creates a GitHub Release for the tag with the MSI attached and
     autogenerated release notes.
5. If the workflow fails, fix the issue on `main`, delete the tag both
   locally and on the remote, then re-tag:

   ```bash
   git tag -d vX.Y.Z
   git push origin :refs/tags/vX.Y.Z
   ```

### Version numbering

Plain semver (`MAJOR.MINOR.PATCH`), no `v` prefix inside the number itself
(the `v` only prefixes the git tag, e.g. tag `v0.2.0` produces MSI version
`0.2.0`). Bump:

- **PATCH** for bug fixes and small internal changes
- **MINOR** for new features (new panels, new metrics, view modes)
- **MAJOR** once the project has a stable public interface worth
  protecting with that signal (not yet reached)

### Local install testing before tagging

Build and sanity-check the MSI locally before cutting a real release:

```powershell
dotnet tool install --global wix --version 5.0.2
powershell -ExecutionPolicy Bypass -File installer\build-installer.ps1 -Version 0.0.0-test
```

Install it, confirm the Start Menu shortcut and Apps & features entry look
right, then uninstall before tagging the real release.

### Why WiX v5, not v7

WiX v7 requires accepting a separate paid Open Source Maintenance Fee EULA
before `wix build` will run (see https://wixtoolset.org/osmf/). WiX v4
lacks the `<Files Include>` component-harvesting shorthand this project's
`.wxs` relies on. WiX v5 has the feature and no separate EULA, so both
`installer/build-installer.ps1` and `.github/workflows/release.yml` pin
`wix --version 5.0.2`. Do not bump past v5 without checking the EULA
situation for the target version first.

## CI

`.github/workflows/ci.yml` builds and publishes on every push and PR
against `main`. It does not build the MSI (that only happens on a tag, in
the Release workflow) and does not run automated tests since none exist
yet.
